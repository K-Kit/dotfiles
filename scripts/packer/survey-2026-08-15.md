## Host

Hetzner Cloud vServer (8 vCPU / 15 GiB). No `svm`/`vmx`, no `/dev/kvm` — nested virt unavailable. **Irrelevant**: Packer's cloud builders execute remotely (create instance → provision → snapshot → destroy), so no local virtualization is needed.

## Blocker

`~/.config/fnox/age.txt` is **missing**, so this box cannot decrypt any fnox secret — including the `digitalocean` and `HERTZNER` tokens that do exist as ciphertext in `config/fnox.toml`. The `fnox` CLI is not installed here either. **`secrets-init` cannot fix this** — it only takes `bws|project` and has no fnox mode; nothing in the repo provisions the age key, which is copied across by hand by design. So until `fnox` is installed (`brew install fnox`) *and* the key is copied over, no fnox-sourced `packer build` and no `vagrant up --provider=digital_ocean` can run — passing the token directly is the way round it. No cloud CLIs are installed either (`doctl`, `aws`, `gcloud`, `terraform`, `tofu` all absent).

## The actual open question: three overlapping provisioning paths

| Path | State | What it gives |
|---|---|---|
| `scripts/cloud/setup.sh` + `custom_bins/hz` | Working, tested | Boot-time provisioning; slow first boot, always current |
| `scripts/coder/{hetzner,digitalocean}-linux` | Working, 68-assertion test suite | Coder workspaces, ephemeral VM + persistent `/home`, DO and Hetzner |
| Packer image bake | Written — `dev-box.pkr.hcl`, never yet run against a real account | Fast boot from a pre-baked image (DO/Hetzner/AWS); image goes stale |

Packer's only real value-add is collapsing `setup.sh`'s runtime into a snapshot — a genuine win for a box created often, worthless for one created monthly.

## Outcome

**Packer stayed.** `dev-box.pkr.hcl` in this directory bakes DigitalOcean, Hetzner and AWS images from one build block reusing `scripts/cloud/{create-user,setup}.sh` **verbatim** — not a reimplementation. A second copy of the provisioning logic is the known failure mode in this repo (statusline drift, `hz` default type, Coder template parity all bit the same way). See `README.md`.

**Vagrant did not.** It is installed and the `digital_ocean` provider loads, but `vagrant up --provider=digital_ocean` overlaps `hz` and the Coder DO template almost exactly — a fourth provisioning path with nothing the other three lack. Left installed (harmless, no config committed) but deliberately unused. Revisit only if a *local* VM workflow appears, which is the one thing `hz`/Coder/Packer genuinely cannot do here.
