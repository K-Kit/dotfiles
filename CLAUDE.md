# CLAUDE.md

Dotfiles for ZSH, Tmux, Vim, SSH and dev tools across macOS, Linux and RunPod, deployed via `install.sh` + `deploy.sh`. `claude/` is symlinked to `~/.claude/` and `codex/` to `~/.codex/` — **edits here change your running environment immediately.**

## Top Rules

- **Direct pushes to main are allowed** — personal repo, no PR overhead. Single branch: `main`; branch worktrees off it. Route only large or structural merges through a tracked PR.
- **Flags are ADDITIVE to defaults unless `--minimal` is used.** `install.sh` and `deploy.sh` enable every component by default; `--no-<component>` disables one; `--minimal` disables all defaults; modifiers (`--append`, `--force`) don't affect defaults. Detail in README.md.
- **Sandbox blocks `git pull`/`merge`/`stash`** here, and `codex exec` crashes on macOS inside it — both need `dangerouslyDisableSandbox: true`.
- **`claude/settings.json` is the global source of truth** (symlinked to `~/.claude/settings.json`). Before staging it, verify it has `statusLine`, `hooks` and `permissions` keys — [`.claude/rules/dotfiles-settings.md`](.claude/rules/dotfiles-settings.md).
- **Secrets are NOT globally exported** (supply-chain defense). Use `setup-envrc` per project via direnv; `secrets-edit` to add or update.
- **Plot with Anthropic style by default** — `from anthro_colors import use_anthropic_defaults`. Colours, the `petri`/`deepmind` alternatives and the full API are in the `anthropic-style` skill.
- **Specs go in `specs/`** (overriding the brainstorming skill's default), plans in `plans/` via `plansDirectory`.
- **Verification is a design problem** — plan *how* you'll verify before starting. If you catch yourself thinking "let me figure out how to verify this", that's EnterPlanMode. Triggers and checklist: [`.claude/skills/verification-planning/SKILL.md`](.claude/skills/verification-planning/SKILL.md).

## Worktrees

`yolo` skips permissions with no worktree. `cw [name]` gives worktree + tmux; `cwy` adds skip-permissions.

| Command | What it does |
|---------|-------------|
| `cwl` | List all worktrees |
| `cwmerge [name]` | Merge worktree branch into parent (auto-detects from inside a worktree) |
| `/merge-worktree` | Claude skill: merge + AI conflict resolution |
| `cwport <name> [dirs...]` | Copy artifacts (out/, logs/) from worktree to main tree |
| `cwrm [--no-merge] <name>` | Merge branch → remove worktree → delete branch |
| `cwclean [--dry-run]` | Remove clean worktrees (no changes, no artifacts) |

`cwrm` **merges by default**; `--no-merge` skips it, `--force` skips artifact warnings. `cwmerge` only recognises `worktree-`-prefixed branches — merge others manually with `git -C <main-tree> merge --ff-only <branch>`. Gitignored files (`.env`, `out/`, `logs/`) do **not** exist in a new worktree. Lifecycle: `cw auth-fix` → work → `cwport auth-fix` → `cwrm auth-fix`.

## Personal Content

This repo is **public** — and a branch in a public repo is public too, so personal working artifacts must not live on any branch here. They go in the separate **private** `dotfiles-personal` repo: `plans/`, `specs/`, `.remember/`, `tmp/`, personal `docs/`, `config/machines.conf`. Those paths are listed in `.gitignore` here so they can't reach public `main` by accident. A superset "personal branch" was rejected because it would have exposed everything it was meant to hide.

`main` is no longer kept "clean for others" — it's just the personal working branch.

## Rules That Prevent Data Loss

**Obsidian sync — promote a vault to bidirectional only by hand**: `ob sync-config --path <vault-path> --mode bidirectional`. Never automate it, and never let `deploy.sh` or `obsidian-sync-check` do it. Any vault whose `sync.log` has no `"Fully synced"` entry yet is force-set to pull-only on deploy; a vault with sync history is never touched, so a manual promotion sticks across redeploys. `obsidian-sync-check [--path <vault-path>]` is **advisory only** and never changes mode. The incident this guards against: in 2026-06/07 a bidirectional sync against an incomplete local copy misread "never downloaded" as "deleted" and propagated the deletions upstream — 135 files lost, recovered via pull-only reconciliation.

**Secrets are per-project, not global.** API keys live in Bitwarden Secrets Manager and are **not** exported into every shell. Reach them with `setup-envrc` in the repo that needs them (direnv), or `with-secrets KEY... -- <cmd>` for one shot. Managed: `OPENAI`/`OPENROUTER`/`ANTHROPIC_API_KEY`, `HF_TOKEN`, `MODAL_TOKEN_ID`/`SECRET`. BWS token at `~/.config/bws/token`; run `secrets-init bws` on a new machine. A project without `.envrc` genuinely cannot see the keys — that is the supply-chain defense working, not a bug.

## Learnings

Project-specific bugs, quirks, decisions and current state. Timestamp `- description (YYYY-MM-DD)`, keep under 20, prune past two weeks — retired entries move to [`docs/tooling-and-packages.md`](docs/tooling-and-packages.md) § Past Learnings.

- The simplify nudge now has a second signal: `simplify_track_reuse.py` counts *runs* of scratch scripts (not writes — writes are iteration) and the Stop hook suggests promoting any that ran 3× with at least one run unchanged. Rules for where a promoted script lands: `claude/rules/reusable-component-promotion.md` (2026-08-01)
- Background-session job dirs (`~/.claude/jobs/<id>/`) have no built-in retention — `cleanupPeriodDays` only covers `~/.claude/projects` transcripts. `custom_bins/claude-jobs-reap` deletes terminal-state job dirs inactive >7d (active-looking states get 30d grace); `claude/hooks/reap_jobs.sh` runs it daily via SessionStart. Deleting a job dir removes the `claude agents` entry only — the transcript and `--resume` survive (2026-08-02)
- **The PermissionRequest hook is `claude/hooks/approval_classifier.py`** (was `auto_classify.py`) — renamed because sessions kept confusing it with Anthropic's harness "auto mode classifier", which is a completely separate path. It now has two backends: the API key first (~1s), then the Claude subscription via `claude -p --model sonnet` when the API path fails for any reason. Both backends run Sonnet 5 as of 2026-08-06; the subscription path's ~9s figure predates that and was measured against Haiku. `claude -p --bare` cannot be used for the fallback — its help states OAuth and keychain are never read — so recursion is stopped by the `APPROVAL_CLASSIFIER_NESTED` env marker instead. State is written to `~/.cache/claude/approval-classifier-health.json` on every attempt and rendered by the statusline as `auto-ant:<key>` / `auto-sub (api down)` / `🔴auto` — the suffix after `auto-` names the *backend*, not the key, so a key labelled `sub` can't be mistaken for the degraded state (2026-08-03)
- **The classifier health file records the last *backend attempt*, not the current state** — `write_health()` runs only on the `classify()` path, so fast-path allows/denies and `AskUserQuestion` surfaces leave it frozen. A single transient API read timeout on 2026-08-05 therefore pinned `🔴auto` for 2.5h while nothing was actually wrong: the API key resolved fine (HTTP 200 in 1.2s) and only fast-pathed tools had run since. The statusline now ages the entry out — past **15m** it renders a dim `auto?` (unknown, not down) for *every* backend, past 6h nothing at all; the backend string is validated before the age tiers so a corrupt file renders nothing rather than a confident `auto?`. When diagnosing a red `auto`, check `~/.cache/claude/approval-classifier.log` for a `NO KEY:` line before suspecting credentials — a socket read timeout and a missing key look identical in the statusline but not in the log (2026-08-05)
- **`custom_bins/claude-tools` is a bash dispatch wrapper, never a binary** — it execs `claude-tools-<os>-<arch>`. Rebuilds go to the arch-suffixed asset; copying one to the generic path makes one platform's build the runtime for all of them, and it exits 0 so the `|| bash statusline.sh` fallback cannot fire. Clobbered twice (`e7c2de0` fixed, `eabeba2` re-broke, undetected 13 days). No script writes that path — it is always a hand-copied rebuild, so the guards are `check-claude-tools-fresh.sh` (asserts `#!` + validates SHA256SUMS) and `tests/test_statusline_classifier.sh`, which now drives the *deployed* dispatcher rather than `target/release/` (2026-08-03)
- **A gate that checks its own variables does not gate the argv it builds.** `claude-spawn` refused `--yolo` + `--remote-control`, but `--remote-control [name]` takes an *optional* argument, and an optional-arg option does not consume a dash-prefixed token — so `-n --dangerously-skip-permissions` reached Claude as two options while the script still believed `yolo=false`. Emit `--opt=value` as one token, sanitise the value, and put `--` before free text. Two knock-ons: `--` strands any option a wrapper *appends* after user args (the `claude()` wrapper's `--channels` did exactly this, silently), and in a test `$TMUX` beats `TMUX_TMPDIR`, so a probe run from inside tmux attaches to the live server and an unconditional `kill-server` takes the user's sessions with it (2026-08-05)
- **Sonnet 5 thinks by default when `thinking` is omitted** — Sonnet 4.6 ran thinking-off by omission, so a request that never set the field silently changes behaviour on the model swap. `max_tokens` caps thinking *plus* response text together, so `approval_classifier.py` (`MAX_TOKENS = 500`) would have spent its whole budget reasoning and truncated before emitting the JSON verdict — parse failure, fail open, a manual permission prompt on every single call. Fixed by passing `thinking: {"type": "disabled"}` explicitly, which is legal only at `effort` `high` or below (none is set; `high` is the default). **The same swap breaks the two backends differently, and fixing one hides the other**: the subscription CLI path has no `max_tokens`, so nothing truncates — instead the child thinks while the hook's deadline drains, and Claude Code 2.1.223 has no `--thinking` flag at all (`--effort low` is the only lever, taking `low|medium|high|xhigh|max`; an unrecognised value merely warns and silently reverts to default effort). Measured 6 interleaved pairs: default effort 4.5–39.4s wall vs `--effort low` 4.5–8.6s, faster in 6/6 (exact Wilcoxon p=0.031) — the tail is the point, not the median. Note the incumbent Haiku showed the same fat tail (one 27.2s draw in six), so "Sonnet is slower" was never established; both models' spread swamped the between-model difference. `tests/test_approval_classifier_thinking.py` pins both the request body and the child argv. **The two backends are mitigated, not equalised**: effort is a behavioural signal rather than a token budget, so `--effort low` reduces thinking without forbidding it, and what actually bounds the CLI path is the timeout clamp `min(SUBSCRIPTION_TIMEOUT_SECONDS, budget)`. `SUBSCRIPTION_MIN_SECONDS` stays at 6 despite the measured 8.6s tail, because a timed-out call and a skipped one converge on the same manual prompt while 5 of 6 measured draws finish under 6s. Any other route in this repo that swaps a 4.6-era model for a 5-era one needs the same audit — and needs it per backend (2026-08-06)
- **Two assertion shapes that cannot fail, both found by Codex in tests I had just proven with mutation testing**: *self-referential* — `assert argv[i+1] == ac.SUBSCRIPTION_EFFORT` compares the argv against the very constant that produced it, so it holds for any value the constant is changed to; and *presence-only* — `assert "--tools" in argv` checks the flag but not its operand, so `"--tools", ""` → `"--tools", "default"` passed while switching the classifier child from **no tools** to **all built-in tools** (`claude --help`: `""` disables all, `"default"` uses all). My mutation harness missed the first because the mutation I picked (`"minimal"`) was *invalid* rather than *valid-but-wrong* — an invalid value trips a membership check that a legal-but-harmful one sails through, so mutations must be drawn from the legal domain. Fix is literals on both sides and ordered-pair assertions; the general sweep is every flag that takes an operand (bare flags like `--safe-mode` are genuinely presence-contracts). Mutation testing proves a test *can* fail, not that it fails for the right *reason* (2026-08-06)
- **fnox is the age-encrypted secrets layer**: `config/fnox.toml` (ciphertext only — the age key at `~/.config/fnox/age.txt` is never in git) is symlinked to `~/fnox.toml` by the `fnox` deploy component. Shell activation auto-exports ALL secrets into the shell, so it is opt-in per shell via `fnox-on`/`fnox-off` (`config/aliases/fnox.sh`) and never wired into zshrc — prefer `fnox exec -- <cmd>` / `fnox get NAME`. Hetzner: `scripts/cloud/hetzner-user-data.sh` renders cloud-init with `TAILSCALE_AUTH_KEY`/`BWS_TOKEN` from fnox, and `HCLOUD_TOKEN="$(fnox get HERTZNER)"` drives hcloud; setup.sh resolves env → fnox → interactive → skip. `TAILSCALE_AUTH_KEY`'s stored ciphertext had a stray space (invalid base64) — repaired in place (2026-08-08)
- **The idle-shutdown watchdog treated a detached agent run as idle.** `active()` counted only `~/.keep-alive`, an established port-22 connection, and an unconditional `who` — so a `cw`/tmux run left detached with no client attached scored idle and the box powered off mid-run, while a forgotten idle login pinned it on forever (the two errors point opposite ways, so neither showed up as "the watchdog is broken"). It now counts a tmux pane whose `pane_current_command` is not a bare shell, and bounds `who` by tty mtime within the idle window; an empty leftover session deliberately still counts as idle, or the watchdog becomes a no-op on a box that keeps billing. `idle-shutdown-check --explain` prints every signal plus a verdict line, and `hz idle status` delegates to it rather than keeping a second copy of the logic. Related: `config/tmux.conf` `history-limit` 10000 → 100000 and `destroy-unattached` pinned off (2026-08-08)
- **The cloud checkout stays at `~/code/dotfiles`, but "one missing `export`" was never a good reason to keep it there.** `config/zshrc.sh` *assigned* `DOT_DIR` without exporting it — while the bash branch of `deploy.sh` had always written `export DOT_DIR=…`, so the two deploy paths disagreed — and consumers written as `${DOT_DIR:-$HOME/code/dotfiles}` hit the literal whenever they weren't children of a login zsh, the normal case for a Claude Code hook. That is an argument for adding the `export`, which is now done. The reasons that actually survive are the ~19 files naming `code/dotfiles` (several in formats that cannot hold fallback logic at all: `.plist`, `.service`, `zed/settings.json`, `codex/rules/*.rules`) and path parity, so a pasted command works on workstation and cloud box alike. `claude/hooks/context_auto_apply.sh` now self-locates via `realpath "${BASH_SOURCE[0]}"` (`~/.claude` → `$DOT_DIR/claude`, so two levels up is the checkout), keeping the literal only for a box without `realpath` — the location is documented, not load-bearing. Rationale at the `DOTFILES=` assignment in `scripts/cloud/setup.sh`; pinned by `tests/test_cloud_provisioning.sh` § DOT_DIR resolution (2026-08-08)
- **`hz create` defaulted to `cpx42` while `hz --help` documented `--type cx23`** — and `hz up` inherits that default *and* implies `--yes`, so the drift billed for a much larger server with no confirmation step. Default is now `cx23`, matching the docs and the `small` preset. The regression test asserts the literal *and* the doc/code parity, because parity alone passes vacuously the moment the help line stops matching the `awk` (2026-08-08)
- **A PAT must never travel via cloud-init user-data**: Hetzner's metadata service serves user-data to *every* local user on the box, so `hetzner-user-data.sh` injects `TAILSCALE_AUTH_KEY`/`BWS_TOKEN` but deliberately not `GITHUB_TOKEN`. `hz create --github-auth` pushes it over SSH after boot instead, on stdin — argv is world-readable through `/proc`, so `gh auth login --with-token` reading stdin is the only safe shape. Bootstrap now writes a verdict to `/var/lib/dotfiles-bootstrap.status` (`running`/`ok`/`failed-create-user`/`failed-setup`), which is what makes `hz wait` able to distinguish "still going" from "died" instead of polling for a marker that never appears (2026-08-08)
- The statusline has **two implementations that must stay in sync**: `tools/claude-tools/src/statusline.rs` (what actually runs) and `claude/statusline.sh` (fallback). Guards added because comments alone can't catch drift: `tests/test_statusline_classifier.sh` asserts both render identically, `claude/hooks/nudge_statusline_parity.sh` fires on edits to either, and `scripts/check-claude-tools-fresh.sh` flags committed binaries older than the source — the silent failure is `darwin-arm64`, which nobody on Linux can cross-compile (2026-08-03)
- **`scripts/coder/` adds Coder templates (Hetzner, DigitalOcean) as a path parallel to `scripts/cloud/`** — ephemeral VM + persistent `/home` volume, idle shutdown via Coder's `coder templates edit --default-ttl`, never the on-box `idle-shutdown-install.sh` watchdog. Three things that bite silently: (1) **the cloud token must be on the provisioner, not in the push shell** — `coder templates push` only uploads a tarball, so `HCLOUD_TOKEN=… coder templates push` is a no-op; both templates therefore accept the token as a `--var` too. (2) **`coder_agent.arch` must match the machine type** — both templates hardcode `amd64` and offer x86 types only, because adding Hetzner `cax*` (ARM) without flipping `arch` builds fine and never connects, with no plan-time error. (3) **In a `.tftpl`, only `$${` is an escape** — `$$var` renders literally as `$$var`, i.e. the shell's PID followed by text; shell variables are written with a single `$`. Caught by rendering the templates with dummy values and running shellcheck on the embedded scripts, which is the closest thing to `terraform validate` available with no terraform/tofu installed. Separately: **Hetzner retired `cx22`** — it is gone from `hcloud server-type list` and no longer accepts creates, so `hz`'s default and the `scripts/cloud/README.md` examples moved to `cx23` (2026-08-08)
- **Three failure modes in the Coder templates that all shared one shape: the safe-looking fallback is the silent one.** (1) The `/home` mount is `nofail` and the helper exits 0 on a missing device — both right, since a workspace that won't boot beats one on the wrong disk — but the result was a workspace that looks *perfectly healthy* while `/home` sits on the ephemeral root disk and is destroyed at the next stop. A warning echoed to the boot console is not a signal; `coder_agent.startup_script` now runs `mountpoint -q` and exits 1, which Coder renders as a red failed-startup in the UI, kept `non-blocking` on purpose so the box stays reachable for the post-mortem. (2) `Environment=CODER_AGENT_TOKEN=…` in the unit file is readable by any local user via `systemctl show`, **whatever mode the unit carries** — tightening 0644→0600 would have looked like a fix and changed nothing; `EnvironmentFile=` is the actual fix, and systemd reads it as root before dropping to `User=`, so 0600 root-only still works. (3) A `cx*` default silently pairs with `ash`/`hil`/`sin` to make a combination that only fails at apply time, because Coder cannot validate one parameter against another — the default moved to `cpx21`, which is valid everywhere, and the *reason* is now a comment at the `default =` line, since the next person will otherwise "fix" it back to the cheaper cx23. Also Hetzner-only: the volume mounts from `runcmd`, i.e. *after* cloud-init's users-groups wrote `/etc/skel`, so a fresh volume had no `.bashrc` — DigitalOcean escapes this only because its `mounts` module runs earlier. `tests/test_coder_templates.py` (68 assertions) renders both `.tftpl`s, checks the `main.tf` ↔ template variable map **in both directions**, shellchecks the embedded scripts, and pins doc/code parity for the default machine type; `tests/mutate_coder_templates.sh` proves it can fail. Writing that suite reproduced the vacuous-pass trap in miniature: `templatefile("${path.module}/…", {…})` made the key extractor grab the `${path.module}` braces, so the key set was empty and the "no dead entries" subset check passed against nothing — a subset assertion is worthless until the set it runs on is pinned non-empty (2026-08-09)
